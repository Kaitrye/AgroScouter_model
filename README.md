# Робот из STEP: первый вариант симуляции

Комплект для Ubuntu 24.04, ROS 2 Jazzy и Gazebo Harmonic (gz-sim 8).
Исходная модель: `robot_model_stp (1).STEP`. Внешняя геометрия экспортирована
из неё, включая корпус, гусеничные модули и манипулятор в текущем положении.
FreeCAD для запуска этой симуляции не нужен. Пересобирать STEP при запуске не нужно.

**Статус:** геометрия, параметры, XML, ссылки на ресурсы и скрипты проверены.
Загрузка и движение визуальных траков проверены в Gazebo Harmonic. Скрипт
`check_motion.sh` проверяет движение робота и поток камеры на твоём компьютере.
Цветной вид модели показан в `preview_colored.png`.

## Быстрый запуск

Распакуй архив. В терминале перейди в папку `robot_sim`, где лежит этот README.
Запускай оболочки именно через `bash`: это работает и из твоего fish.

Если пакет ROS-моста или инструменты сборки ещё не установлены:

```bash
sudo apt update
sudo apt install ros-jazzy-ros-gz cmake g++
```

Это дополнения к уже установленному ROS 2 Jazzy. Скрипт ожидает его
в `/opt/ros/jazzy`. Установка самого ROS 2 в этот архив не входит.

Первый терминал — симулятор, мосты, TF камеры и обработчик команд:

```bash
bash start_sim.sh
```

При первом запуске скрипт собирает небольшой плагин анимации гусениц в
`build/track_animation`. После изменения его исходников он пересобирается
автоматически.

Второй терминал, из той же папки:

```bash
bash teleop.sh
```

Клавиши управления выводятся в окне терминала: `i` — вперёд, `,` — назад,
`j`/`l` — поворот, `k` или пробел — остановка. Держи клавишу движения нажатой;
окно этого терминала должно быть активным. Поддерживаются английская и русская
раскладки. Команды повторяются с частотой
10 Гц и обнуляются через секунду после последнего нажатия. Скорость также
ограничена моделью.
Закрывай комплект через Ctrl+C в первом терминале.

Без графического окна, с теми же ROS-топиками:

```bash
bash start_sim.sh gui:=false
```

Чтобы отдельно посмотреть модель без ROS-моста:

```bash
bash start_gazebo.sh
```

Для такого режима ROS-топики не создаются. Управление из `teleop.sh`
появится только при запуске через `start_sim.sh`.

## Первая проверка

Оставь `start_sim.sh` запущенным, убедись, что мир не на паузе, и закрой
телеуправление, чтобы команды не конфликтовали. В другом терминале:

```bash
bash check_motion.sh
```

Робот должен проехать вперёд, остановиться, повернуться и снова остановиться.
Проверка занимает около 13 секунд симуляционного времени. Она проверяет
изменение **истинной позы**, направление движения, остановку и приход кадров
камеры. Последняя строка содержит `PASS=True` или `PASS=False`.
Это проверка запуска, а не калибровка реальной динамики.

## Что получено из CAD

Система координат симуляции: X вперёд, Y влево, Z вверх, единицы — метры.
В STEP единицы — миллиметры; исходная ось Y направлена вверх.
Преобразование: `X_ros = (Z_cad + 201.458483) / 1000`,
`Y_ros = (X_cad - 595) / 1000`,
`Z_ros = (Y_cad + 76.445175) / 1000`.

| Величина | Значение | Основание |
|---|---:|---|
| Общая длина по внешней геометрии | около 0.575 м | CAD, включая манипулятор |
| Общая ширина | около 0.966 м | CAD, включая выступающие детали |
| Общая высота | около 0.919 м | CAD |
| Расстояние между центрами лент | 0.810125 м | CAD |
| Ширина каждой ленты | 0.120 м | CAD |
| Внешняя длина ленты | 0.472134 м | CAD |
| Внешняя высота ленты | 0.324818 м | CAD |
| Камера: X, Y, Z относительно base_link | 0.161918, 0.019264, 0.865439 м | оценка оптического центра по верхней камере в CAD |

Направление «вперёд» выбрано по лицевой стороне верхней камеры, вдоль
исходной +Z. Это интерпретация геометрии: проверь её, когда получишь доступ
к роботу. Если верхняя камера предназначена смотреть назад, можно изменить
её yaw или позже переопределить оси модели. Две боковые камеры, большая
камера и лидар присутствуют в CAD-визуализации, но пока не создают отдельных
датчиков. Активна одна верхняя виртуальная камера.

`config/geometry.json` содержит размеры и преобразование координат.
`config/cad_parts.json` содержит имена и исходные габариты 637 конечных
компонентов сборки; компонент основного шасси сам содержит 309 твёрдых тел.
Самые мелкие внутренние электронные компоненты опущены только в визуальной
сетке. STL имеет около 497 тысяч треугольников суммарно и используется для
отображения. В расчёте столкновений используются простые формы.

Цвета видимых деталей взяты с фотографий в `images`: серебристый каркас,
чёрные гусеницы и камеры, жёлтая площадка, синий аккумулятор и зелёный
кронштейн. Стеклянные панели полупрозрачны. Палитра находится в
`config/parameters.json`. Для окраски исходный `body.stl` разделён на
несколько сеток по материалам; после замены исходного STL запусти
`python3 tools/colorize_mesh.py`, затем `python3 tools/generate_model.py`.

## Предварительная физика

| Параметр | Начальное значение |
|---|---:|
| Масса корпуса с оборудованием и зафиксированным манипулятором | 32 кг |
| Масса каждого гусеничного модуля | 4 кг |
| Суммарная масса | 40 кг |
| Трение: продольное / поперечное | 1.0 / 0.7 |
| Коэффициент эффективности поворота | 0.8 |
| Максимальная линейная скорость | 0.4 м/с |
| Максимальная угловая скорость | 0.6 рад/с |
| Максимальное линейное ускорение | 0.4 м/с² |
| Максимальное угловое ускорение | 0.8 рад/с² |
| Таймаут входных команд | 0.5 с |

**Это допущения, а не характеристики реального робота.** Масса 40 кг выбрана
как стартовая для этой геометрии. Центр масс корпуса оценён по объёмам CAD
при условии одинаковой плотности; настоящие материалы и массы неизвестны.
Инерции рассчитаны для однородных прямоугольных объёмов с заданными массами.
Они положительные и согласованы с размерами, но не являются измеренными.

Гусеницы моделируются через `TrackedVehicle` и по одному `TrackController`
на сторону: движение обеспечивается скоростью контактной поверхности.
Ленты жёстко соединены с корпусом. Поверх CAD-модели движутся визуальные
траки по внешнему треугольному контуру, который генератор извлекает из STL
каждой гусеницы. Их скорость берётся из команд для левой и правой сторон, поэтому при
повороте стороны анимируются независимо. Эти траки не имеют массы и контакта;
физику движения по-прежнему рассчитывает `TrackController`. Колёса остаются
неподвижными, отдельных шарниров между звеньями ленты нет. Деформация, натяжение,
грунтозацепы и момент моторов не моделируются. Это упрощённая модель для
работы с управлением и локализацией, не для исследования механики гусениц.

Форма контакта каждой стороны — нижняя капсула (бокс и два цилиндра)
и верхний бокс. Конверсия боксов корпуса сохраняет его общий габарит,
но заполняет пустоты рамы: проникновение предметов внутрь корпуса в этом
варианте не воспроизводится. Манипулятор имеет неподвижный габаритный бокс.
В `preview.png` справа показаны габаритные объёмы упрощения; гусеницы для
наглядности показаны целым боксом, фактический контакт в SDF — капсула.

## Изменение параметров

Все параметры находятся в `config/parameters.json`. После изменений:

```bash
python3 tools/generate_model.py
```

Затем перезапусти симуляцию. Это обновит SDF и сцену; STEP и сетки
обрабатывать повторно не нужно. Генератор использует только стандартную
библиотеку Python.

Если CAD-отображение слишком тяжёлое для ноутбука, поставь
`"visual_mode": "simplified"` и запусти генератор. Физика и размеры
контактных поверхностей останутся такими же, внешний вид станет проще.
Для камеры можно сначала уменьшить разрешение до 320×240 и частоту до 10 Гц.

## ROS-топики и координаты

| ROS-топик | Тип | Назначение |
|---|---|---|
| `/cmd_vel` | `geometry_msgs/msg/Twist` | команды пользователя |
| `/robot/cmd_vel` | `geometry_msgs/msg/Twist` | команды после повтора и таймаута |
| `/odom` | `nav_msgs/msg/Odometry` | кинематическая одометрия привода |
| `/ground_truth/odom` | `nav_msgs/msg/Odometry` | поза и скорость из физической симуляции |
| `/camera/image_raw` | `sensor_msgs/msg/Image` | изображение верхней камеры |
| `/camera/camera_info` | `sensor_msgs/msg/CameraInfo` | параметры виртуальной камеры |
| `/clock` | `rosgraph_msgs/msg/Clock` | симуляционное время |
| `/tf` | `tf2_msgs/msg/TFMessage` | odom → base_link |
| `/tf_static` | `tf2_msgs/msg/TFMessage` | base_link → camera_link → camera_optical_frame |

Положение `base_link` — на уровне пола между центрами гусениц, а не
в центре масс. `camera_link`: X вдоль взгляда камеры. `camera_optical_frame`:
Z вперёд, X вправо, Y вниз, как ожидают OpenCV и ROS изображения.
`ground_truth` имеет начало координат `world`; его TF не публикуется в общий
ROS `/tf`, чтобы не создавать вторую конкурирующую связь для `base_link`.

Для узлов локализации включай `use_sim_time:=true`. Кинематическая одометрия
не равна истинной позе при проскальзывании. В TrackedVehicle Harmonic она
рассчитывается из скорости лент как одометрия дифференциального привода;
при эффективности поворота меньше 1 её угол может расходиться с командным.
Сравнивай алгоритм с `/ground_truth/odom`, а не принимай `/odom` за эталон.

Начальные параметры камеры: 640×480, 20 Гц, горизонтальный угол 60°.
Фокусное расстояние примерно 554.26 пикселя. Реальные K и дисторсия камеры
пока неизвестны; используй приходящий CameraInfo для работы в симуляции.
Сцена содержит пол, две стены, препятствие и низкую ступеньку. ArUco-маркеры
пока не добавлены: их нужно размещать с известными размерами и позами.

## Если что-то не запускается

- `ros2` или пакет `ros_gz_bridge` не найден: проверь ROS 2 Jazzy и установку
  пакетов выше. Скрипты сами загружают `setup.bash`.
- Модель не найдена: запускай скрипты из распакованной папки; они задают
  `GZ_SIM_RESOURCE_PATH` относительно своего расположения.
- Робот виден, но не движется: проверь, что мир не на паузе, посмотри вывод
  первого терминала, особенно ошибки `TrackController` и физического движка.
  Гусеничный привод требует поддержки изменения контактной поверхности
  в DART / gz-physics. На нестандартной или старой установке DART эта
  возможность может отсутствовать. Пришли лог запуска; не заменяй привод
  произвольным перемещением позы — это исключило бы контактную физику.
- Чёрное или отсутствующее изображение: проверь сообщения `Sensors` / Ogre2.
  Можно временно перейти на простую визуализацию и уменьшить разрешение.
- Уточнение массы и трения не требует переделки геометрии: меняй JSON,
  запускай генератор, повторяй проверку движения.
