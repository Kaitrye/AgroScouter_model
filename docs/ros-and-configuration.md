# Параметры и ROS-интерфейс

Параметры модели хранятся в [`config/parameters.json`](../config/parameters.json), а её геометрические данные — в [`config/geometry.json`](../config/geometry.json).

## Интерфейс моторов

При запуске через `start_sim.sh` симуляция принимает команды в `/motors` в
формате реального контроллера. `[40, 40]` ведёт вперёд, `[-40, -40]` назад,
`[-30, 30]` поворачивает влево, `[0, 0]` останавливает. Каждое значение
ограничивается диапазоном −100…100. При отсутствии новых команд более
`command_timeout_s` привод останавливается. Внутри модели команды переходят
в скорости гусениц через Gazebo TrackedVehicle; уже заданная разница скоростей
левых и правых моторов применяется после этого перехода.

`/encoders` публикуется с частотой 50 Гц. Каждый счётчик интегрирует
скорость своей гусеницы после применения погрешности мотора, а не смещение
корпуса по `/ground_truth/odom`. Поэтому при проскальзывании гусеница
продолжает набирать тики, даже если корпус почти не движется. Скорости
поступают через внутренние топики `/robot/left_track/speed` и
`/robot/right_track/speed` (`std_msgs/msg/Float64`); при прекращении потока
скоростей счётчики останавливаются по таймауту.

Это виртуальные энкодеры скоростной модели привода: в Gazebo нет
отдельной физики вала, редуктора или заклинивания мотора под нагрузкой.
`encoder_ticks_per_meter` (пока 1000) и `motor_command_speed_m_s` (скорость
каждой гусеницы при команде 100, пока 0,4 м/с) задаются в
`config/parameters.json`; для сравнения с настоящим роботом их надо измерить.

Для ручной проверки при запущенном `start_sim.sh`:

```bash
source /opt/ros/jazzy/setup.bash
ros2 topic pub --rate 10 /motors std_msgs/msg/Int32MultiArray '{data: [40, 40]}'
```

Остановка — Ctrl+C: по истечении таймаута команда сбрасывается.

## Изменение параметров

Все параметры находятся в `config/parameters.json`. После изменений:

```bash
python3 tools/generate_model.py
```

Затем перезапустите симуляцию. Это обновит SDF и сцену; STEP и сетки
обрабатывать повторно не нужно. Генератор использует только стандартную
библиотеку Python. Если менялась геометрия передней площадки, камеры или IMU в `robot_visual_edit.blend`, выполните вместо
этого `bash tools/sync_camera_mount.sh`: эта команда экспортирует новые сетки
и обновит положение камеры и IMU в параметрах.

Если CAD-отображение слишком тяжёлое для ноутбука, установите
`"visual_mode": "simplified"` и запустите генератор. Физика и размеры
контактных поверхностей останутся такими же, внешний вид станет проще.
Для камеры можно сначала уменьшить разрешение до 320×240 и частоту до 10 Гц.

## ROS-топики и координаты

| ROS-топик | Тип | Назначение |
|---|---|---|
| `/motors` | `std_msgs/msg/Int32MultiArray` | команды моторам `[левый, правый]`, каждое значение от −100 до 100 |
| `/encoders` | `std_msgs/msg/UInt32MultiArray` | тики виртуальных энкодеров гусениц `[левый, правый]` |
| `/robot/cmd_vel` | `geometry_msgs/msg/Twist` | внутренняя команда Gazebo после пересчёта и таймаута |
| `/odom` | `nav_msgs/msg/Odometry` | кинематическая одометрия привода |
| `/ground_truth/odom` | `nav_msgs/msg/Odometry` | поза и скорость из физической симуляции |
| `/camera/image_raw` | `sensor_msgs/msg/Image` | изображение камеры, направленной вниз |
| `/camera/camera_info` | `sensor_msgs/msg/CameraInfo` | параметры виртуальной камеры |
| `/scan` | `sensor_msgs/msg/LaserScan` | круговой скан нижнего лидара |
| `/imu/data` | `sensor_msgs/msg/Imu` | ориентация, угловая скорость и линейное ускорение IMU |
| `/clock` | `rosgraph_msgs/msg/Clock` | симуляционное время |
| `/tf` | `tf2_msgs/msg/TFMessage` | odom → base_link |
| `/tf_static` | `tf2_msgs/msg/TFMessage` | base_link → camera_link → camera_optical_frame, base_link → lidar_link и base_link → imu_link |

Положение `base_link` — на уровне пола между центрами гусениц, а не
в центре масс. `camera_link`: X вдоль взгляда камеры. `camera_optical_frame`:
Z вперёд, X вправо, Y вниз, как ожидают OpenCV и ROS изображения.
`ground_truth` имеет начало координат `world`; его TF не публикуется в общий
ROS `/tf`, чтобы не создавать вторую конкурирующую связь для `base_link`.

Сканер лидара расположен внутри его CAD-корпуса в `(−0.1194, −0.0065, 0.5364)` м
относительно `base_link`. В Gazebo его топик `/robot/lidar/scan` переводится ROS-мостом
в `/scan`; частота 10 Гц, 720 отсчётов, диапазон 0.15–12 м. Корпус лидара взят из STEP и перенесён под заднюю перекладину; два боковых цилиндра на той же высоте
восстановлены по фото и пока остаются только визуальными деталями.
Частота и дальность лидара — предварительные настройки симуляции.

IMU расположен в `(0.321, 0, 0.581)` м относительно `base_link` и повернут
на +90° вокруг Z. Его топик Gazebo `/robot/imu/data` переводится в ROS
`/imu/data` с `frame_id=imu_link`. Частота 100 Гц. Текущее положение
датчика при запуске принимается за начальную ориентацию `(0, 0, 0)`: его
поворот на пластине не добавляется к начальным показаниям. TF сохраняет
геометрическое расположение и поворот корпуса датчика относительно `base_link`.
Габарит и расположение оценочные; калибровка шума и смещения реального IMU
не выполнялась.

Для узлов локализации включите `use_sim_time:=true`. Кинематическая одометрия
не равна истинной позе при проскальзывании. В TrackedVehicle Harmonic она
рассчитывается из скорости лент как одометрия дифференциального привода;
при эффективности поворота меньше 1 её угол может расходиться с командным.
Сравнивайте алгоритм с `/ground_truth/odom`; `/odom` не служит эталоном.

Корпус нижней камеры скопирован с верхней камеры исходного STEP и повёрнут
объективом вниз; положение виртуальной камеры `(0.276, 0.238, 0.550)` м.
Круглая камера из STEP-компонента 27 опущена под единую жёлтую пластину,
но отдельного ROS-изображения пока не выдаёт.
Начальные параметры камеры: 640×480, 20 Гц, горизонтальный угол 60°.
Фокусное расстояние примерно 554.26 пикселя. Реальные K и дисторсия камеры
пока неизвестны; используйте приходящий CameraInfo для работы в симуляции.
Сцена содержит пол, две стены, препятствие и низкую ступеньку. ArUco-маркеры
пока не добавлены: их нужно размещать с известными размерами и позами.
